## 1. 结论

1. 项目已经越过「能不能跑」阶段：核心 JT808 接入、会话与分包、应答配对、补传、存储后端、苏标附件、1078 媒体接收、管理面查询都已有可运行实现。
2. 真正的上线缺口不再是功能广度，而是数据路径的收尾与可运维性：SQL 后端下业务 API 仍依赖空的 `Device.SessionID` 找会话，下行命令 outbox 只覆盖部分入口，业务 API 没有鉴权，服务没有指标与就绪探针，媒体/附件落盘没有生命周期管理。
3. 本次核对最终快照：`go build ./...`、`go test ./...` 全绿，outbox 重投已有 7 个专项测试，迁移版本断言已更新到 `20261110`；PR #35 已合入 `main`，`dev/uplink-sink` 改造线收尾。
4. 建议的上线最小集是 R3 → R1 → N1 → R2 → N2 → R4 → R5（约 12–17 人日）；视频、拍照、远程升级三条扩展链路按产品范围决定是否追加 R6–R8。

## 4. 已合入：`dev/uplink-sink` 三条线（PR #35）

> 本节描述的是已合入 `main` 的 #35 内容，保留作为后续 R2/N1/N2 的事实依据。

### 4.1 依赖注入骨架（S1/S2）——已完成

- 注册表按「服务端上行 / 平台下行 / 模拟器」分组，处理函数改为方法，依赖通过 `ProcessorDeps` 注入。
- 默认仍保留 `Default()` 回退，装配层以外不应再新增包级单例调用。
- 验收口径：81 个 MsgID / 42 个处理函数不变，注入独立内存存储后测试互不污染。

### 4.2 应答与连接语义（S4）——已完成

- 固定应答类上行消息先回 `0x8001`（`0x0801` 回 `0x8800`），再执行业务。
- 业务错误除 `ErrDeviceNotFound` 外，一律「已应答 + 记日志 + 不关连接」；钩子仍然触发。
- 0x0200 的 at-most-once 语义已在代码注释中标注。
- 与设计文档的偏差：S4 实际先于 S3 实施。语义变化早落地可以接受，但 S3 完成后需要回补一次行为等价性回归。

### 4.3 下行命令 outbox 与重投——已合入，待 N1/R2 收尾

已具备：

- `command_outbox` 表、幂等键 `(phone, idempotency_key)`、状态机 `pending → acked | failed`。
- 内存与 SQL 两套 `CommandRepository`，含 `ClaimPending`/`BeginAttempt`/`ReleaseAttempt`/`ScheduleRetry`/`ExpirePending`。
- `internal/command/replay.go`：租约占用、过期清理、指数退避、失败事件回收、启动即重投。
- 6 条下行入口已改为「先入 outbox 再发送」，重复 `Idempotency-Key` 不二次下发。
- `GET /commands/:commandId` 可查状态与尝试次数。

还差：

1. **覆盖不完整**：33 条业务路由中多条下行/触发入口仍直发，包括 0x8300、0x8302、0x8304、0x8500、0x8203、0x8103、0x9208、0x9205、0x0805 等；0x9101/0x9102/0x9201/0x9202/0x9206 甚至没有 HTTP 入口（见 R6）。当前只有 6 条进入 outbox。
2. **没有 outbox 指标**：pending 数、重投次数、过期数、租约冲突数均不可观测。
3. **未定义「哪些入口可以豁免 outbox」**：查询类、无下行应答类需要明确白名单，否则后续新增路由会继续绕开可靠性机制。
4. **缺少业务 API 层测试**：outbox 已有仓储与 replay 单测，但 `internal/api` 没有 HTTP 入口测试，接入状态码、幂等头、错误返回未受保护。

已补齐：迁移版本断言已到 `20261110`，`internal/command` 已有 7 个重投专项测试（重启、离线等待、次数耗尽、跨实例幂等、过期、退避、同步发送失败）。

### 4.4 仍未启动的上行 Sink 改造

[uplink-sink-design.md](./uplink-sink-design.md) 的 S3/S5/S6 尚未实施：

- S3：归一化记录 + `local-db` 适配器（按位置/行业/参数/媒体四类拆分）。
- S5：配置化 Sink 与 `noop` 路由。
- S6：可选异步投递（默认关闭）。
- S3 是 S5 的前置；底座与 S3a/S3b 必须先落，S3c/S3d 之后可并行。该线不阻塞单机上线，但阻塞后续 MQ 接入。

## 6. 依赖关系与执行顺序

本轮为串行推进，顺序与 5.1 的「顺序」列一致：

```
R3（SQL 会话定位）
 └─→ R1（CI + race 基线）
      └─→ N1（outbox 分档）
           └─→ R2（下行入口审计 + 豁免清单）
                └─→ N2（上行可靠性配置化）
                     └─→ R4（可观测性与优雅关机）
                          └─→ R5（鉴权/审计 + 部署运维 + 保留期清理）
```

条件项与 P1/P2 的依赖不变：

```
R6（1078 下发） ─┐
R7（0x0801 组装 + 0x0805 落盘） ─┴─→ U3（媒体生命周期）
R8（升级工作流）独立
S3a → S3b → S3c/S3d → S5 → S6
P2.x 仅在触发条件满足后启动
```

串行硬约束：

1. R3 必须先做：会话定位不修，SQL 后端下所有下行验证都会误判为「设备离线」。
2. R1 紧随其后，否则无法判断后续改动是否引入回归。
3. N1 必须先于 R2：分档决定了 R2 各入口接入的目标模式与白名单口径。
4. N2 在 R2 之后：上行可靠性配置需要复用下行入口审计后统一的配置与错误处理约定。
5. R4 接在 N2 之后，指标要覆盖已稳定的 outbox 与上行 spool。
6. R5 最后收口鉴权、部署与保留期。

可并行（非本轮范围）：R6/R7 可并行；U3 必须在其一完成后启动；S3 的四类可在底座完成后并行。

## 7. 上生产最小集合

### 7.1 核心最小集（不依赖视频/拍照/升级）

按 5.1 的串行顺序：

- R3：SQL 后端会话定位修复，下行不再依赖 `Device.SessionID`。
- R1：CI 覆盖 `dev/*`、race 全跑、outbox 回归纳入。
- N1：outbox 分档，单机默认 `memory`，`durable` 保留重启重投能力。
- R2：下行入口覆盖或白名单，业务 API 测试。
- N2：上行可靠性配置化，0x0704 与报警默认至少一次且应答前已落盘。
- R4：健康检查、就绪探针、基础指标、优雅关机。
- R5：业务 API 鉴权/审计、compose、迁移、备份恢复、回滚手册、保留期清理、压测。

估算：约 12–17 人日。完成这七项后，单机版可承载「注册/鉴权/定位/报警/参数/文本/电话簿/透传」等核心业务上线。

### 7.2 按交付范围追加

- 视频：R6 + U3（约 5–8 人日），U2 仅在产品要求完整视频能力时追加。
- 拍照/多媒体：R7 + U3（约 7–10 人日）。
- 远程升级：R8（约 5–7 人日）。

### 7.3 上线门槛

1. `gofmt -l .`、`go build ./...`、`go vet ./...`、`go test -race ./...` 全绿。
2. SQLite/MySQL 后端下，所有下行路由都能按手机号找到在线会话，不依赖 `Device.SessionID`。
3. 至少一次「进程重启后 pending 命令重投」与「设备离线期间命令等待」的端到端演练。
4. 业务 API 无凭证不可写、不可控车。
5. `/readyz` 能反映存储不可用、outbox 过期堆积、媒体/附件磁盘异常。
6. 备份恢复与迁移失败回滚各演练一次。
7. 若开启媒体/附件，磁盘保留策略与告警已配置。

## 9. 可以砍掉或明确延后的项

1. **0x0801 扩展定位项结构化解析**：未知项已保留 raw，且 0x0200 的类型化能力覆盖报警主路径；除非证据链要求逐字段检索，否则不做。
2. **1078 音频、H.265、转码、分发、TCP 推送**：v1 若只做「预览留证」，保留 UDP + H.264 落盘即可；完整视频平台能力延后到 U2。
3. **0x9207 与 0x1003/0x1005**：与视频完整度绑定，v1 不做实时预览时可一并延后。
4. **远程升级工作流**：若 v1 不承诺远程升级，0x8108/0x0108 的目录与结果记录已够用，R8 整体延后。
5. **分布式运行态、Gateway 模式、MQ Sink**：单机版没有触发条件前不启动；不要为了「看起来像分布式」提前引入 Redis/Kafka。
6. **2011 消息头级识别与厂商扩展包**：车队以 2013/2019 终端为主时不做；有真实 2011 终端再启动 P2.6。
7. **0x1FC4**：属粤标扩展，非苏标升级主链；没有粤标市场时不实现。
8. **0x0802 检索结果落库**：终端可重查，保留有界内存即可；写入库只会增加膨胀与清理成本。
9. **管理面 RBAC/细粒度审计**：token + 按 key 限流已覆盖单团队运维；多租户前不做。
10. **高基数指标**：不要按手机号打标签；只做总数、按 MsgID、按版本、按结果分类。

## 10. 下一步建议

本轮按串行顺序推进，每项独立提交、独立报告：

1. **先做 R3**：修 SQL 后端会话定位，改为运行时会话注册表按手机号定位连接；先补回归测试再改实现。这是最紧急的正确性缺口。
2. **再做 R1**：把 `dev/*` 分支纳入 CI，跑 `gofmt/build/vet/test -race`，并确认 outbox/replay 测试在 CI 中真实执行。本机绿灯只是起点，不是发布基线。
3. **再做 N1**：给 `commandOutbox.mode` 分档（`off`/`memory`/`durable`），单机默认 `memory`；`durable` 保留当前重启重投能力，不再是唯一主路径。
4. **再做 R2**：以 N1 的分档为前提审计全部下行入口，接入 outbox 或写入豁免白名单；补 `internal/api` 测试。
5. **再做 N2**：`uplink.reliability` 按消息分类配置；at-least-once 必须先落本地 spool 再应答，测试要验证「应答前已落盘」。
6. **再做 R4 与 R5**：可观测性/健康检查/优雅关机收口后，再补鉴权审计、部署产物、保留期清理与压测。
7. **同时做范围决策**：明确 v1 是否包含视频、拍照、远程升级。若不包含，直接按核心最小集推进；若包含，提前把 R6/R7 → U3 与 R8 排进队列，避免上线前临时补链路。
